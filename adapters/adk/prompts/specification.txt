AUTHORITY MAPPING:
- REQ, DATA, and INTERFACE may become REQUIRED_FIELD or RELATION_CONSTRAINT only
  when explicit.
- Event-driven UI behavior becomes USER_INTERACTION.
- State lifecycle behavior becomes STATE_TRANSITION.
- Persisted records, payload shapes, storage keys, and naming rules become DATA_CONTRACT.
- Required routes and route behavior become ROUTE_CONTRACT.
- Conditional display behavior becomes VISIBILITY_RULE.
- QUALITY and CONSTRAINT become MAX_VALUE or RELATION_CONSTRAINT only when measurable.
- Explicit prohibitions become FORBIDDEN_CAPABILITY.
- Do not promote SHOULD or MAY guidance to stronger semantics. Preserve source_level.
- Split compound requirements into separate invariants when needed for complete coverage.
- Run a final coverage audit over every eligible_item_id before returning.

COVERAGE RULES:
- Every eligible MUST or MUST_NOT item must produce one or more invariants, or a
  gap beginning with its exact item ID when no supported invariant can represent it.
- Gaps are a last resort, not a substitute for supported runtime behavior.
- Do not omit counter, keyboard, mouse, route, persistence, reset, reload,
  restoration, or visibility behavior. Documentation and tooling requirements
  still require exact item-ID gaps when unsupported.
- Use DATA_CONTRACT only for an explicit persisted or exchanged data shape,
  dependency-manifest entry, record, payload, storage key, or naming contract.
  Do not use it for a tool choice, language-version target, setup operation,
  dependency operation, quality process, or other implementation workflow.
- For API schemas, use DATA_CONTRACT with the schema or operation as subject. Do
  not emit context-free REQUIRED_FIELD invariants for request or response fields.
- For path and query parameters, preserve the operation and route context.
- For routing requirements, include every required route and any explicit routing
  library or fallback-selection contract.
- For persistence requirements, include every explicit preferred and fallback
  implementation path.
- For filtering requirements, preserve model filtering, selection changes,
  visibility, and reload restoration when specified.
- For aggregate controls, preserve aggregate state after individual changes and
  after related bulk actions.
- Preserve every explicit follow-on synchronization, reset, reload, restoration,
  and side effect in acceptance criteria.
- Never compress user events, state transitions, routes, persistence shapes, or
  visibility rules into REQUIRED_FIELD.
- Use MAX_VALUE only for a literal numeric maximum.
- Use RELATION_CONSTRAINT for dynamic comparisons such as budget_used <= budget;
  never replace a field relationship with a hard-coded number.
- Use FORBIDDEN_CAPABILITY only for an explicit prohibition.
- Before returning, verify each eligible item ID appears in at least one invariant
  citation or at the beginning of a gap.
